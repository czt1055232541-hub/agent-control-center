# ACC 插件依赖审计与剩余迁移

基线：v0.13.1。以下来自 Python AST 导入扫描和相关实现阅读，不以 `native` 标签作为解耦证明。扫描只覆盖绝对 `from feishu_stack.modules...` 导入，动态导入、相对导入及前端请求需另验。

## 已确认的边界

- DSH 适配器仅通过 HTTP 访问 ACC，不导入其 Python 模块。
- 外部 ACC 发行包可通过 entry point 提供 API 和独立 HTML 页面；不需要改变 DSH 或 ACC 前端编译入口。
- 内建功能已独立拥有路由和页面入口，但不是十个可单独卸载的发行包。
- 禁用开关移除路由、清单和生命周期贡献；不阻止现有静态导入加载功能包。

## 剩余依赖与处理顺序

| 依赖 | 实际用途 | 下一阶段处理 | 验收证据 |
| --- | --- | --- | --- |
| api → modules.operations.operations | 操作锁、记录与指标 | 已迁入 core.operations；旧路径保留同一模块对象别名 | 新旧路径对象一致；并发拒绝及配置失败后释放锁回归 |
| plugins.__init__ → 十个功能入口 | 内建插件描述发现时立即导入业务模块 | 将描述与运行实现分离，禁用功能不加载运行入口 | 新进程禁止导入被禁用模块仍能启动框架 |
| Dashboard → Agent 聚合；Agent 聚合 → 日志诊断 | 聚合页面与解释性诊断混合 | 拆开聚合数据和诊断贡献，不直接添加互相循环的 requires | 单独启用/禁用后无反向调用、无依赖环 |
| 日志诊断 → Agent / Local Tools / Model Provider | 跨功能诊断和流接口 | 显式服务贡献与可用性判断，或将路由归还实际功能所有者 | 对应功能禁用后不探测其业务服务 |
| Backup → Model Provider.codex_config | 备份清理实现放在模型配置模块 | 将通用备份策略与模型配置操作分离，保留旧入口 | 隔离目录中的保留策略、路径边界及未授权拒绝 |
| operations.cli / stack_actions → 多功能模块 | 旧命令与组合操作 | 保留用户 CLI 兼容，将业务编排视为功能而非框架发现机制 | 旧命令路由与无副作用模拟回归 |

`core.status` 虽未导入功能包，仍包含 Codex/Provider 特定状态采集；目录名不是框架中立性的证据。后续不能仅将业务文件搬到 core 就宣称完成。

## 实施约束

每次只迁移一个边界，先增加失败测试，再保持旧 URL、命令和导入兼容。不得执行真实备份清理、Provider 切换或代理启停作为测试。完成新进程隔离测试后，再做全量测试、构建、定向 ACC 重启和版本标签；不改 DSH 源码，不重启 DSH 来替代对接入问题的诊断。

浏览器视觉/点击和完整 DSH 会话回归仍是独立验收门槛；依赖迁移不能替代这些证据。
