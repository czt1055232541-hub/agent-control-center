## 3. 防泄密设计完整性审查

| 防线 | 方案设计 | 验证意见评价 | 审计意见 |
|------|---------|------------|---------|
| 角色白名单 | allowed_roles + X-Control-Token + 角色映射 | ✅ 合理 | ✅ 设计完整，复用现有鉴权体系的决策正确 |
| 入库脱敏 | 正则替换 API Key/IP/ID，规则可配置 | ✅ 合理，建议加前后边界约束 | ✅ 基础覆盖到位，"建议加强正则边界"为完善性建议，非缺陷 |
| 审计日志 | 保留90天，不记录正文，仅 entry_id+action | ✅ 结构完整 | ✅ 设计合理，保留期可配置是加分项 |
| 外发拦截 | 仅绑定127.0.0.1，confidential不索引，导出受控 | ✅ 强约束 | ✅ 层层递进，方案中有3道外发控制，覆盖充分 |
| 模型本地化 | 全部本地加载，不调用外部API | ✅ 不依赖云端 | ✅ 与控制中心安全域一致 |

**风险最小化设计**
- confidential 级别正文不进入向量索引 → 即使检索层被绕过，机密内容也不在可检索范围内
- 脱敏发生在入库管线而非检索阶段 → 一次脱敏，全局受控
- 审计日志不记录条目正文 → 日志泄露也不暴露知识内容

**改进建议**（来自运维验证官，我认可）：

1. 脱敏正则 `sk-...` 加 `\b` 边界约束避免误伤
2. 管理员的跨级查看在审计日志中增加高亮标记位
3. 补充：file_watch 启动时应对监控目录做初始完整性扫描 + 脱敏确认

**评价**：防泄密设计 **完整、可落地**，覆盖入库→存储→检索→导出全链路。

## 4. 风险分析充分性审查

### 方案原风险表（6项）

| 风险 | 缓解措施 | 审计意见 |
|------|---------|---------|
| 嵌入模型首次下载失败 | 预置模型文件 + 离线回退 | ✅ 缓解措施具体可行 |
| ChromaDB 向量索引损坏 | API 重建索引，元数据独立 | ✅ 索引与元数据分离架构合理 |
| 大文件索引性能 | 分块 + 异步 + 10MB上限 | ✅ 上限控制 + 异步处理 |
| 敏感信息漏脱敏 | 多层防线 | ✅ 入库脱敏 + 检索过滤 + 外发拦截 |
| 版本膨胀 | 自动清理 + 可配置保留数 | ✅ 默认10版，可配置 |
| SQLite 并发写入瓶颈 | 单写入者 + WAL 模式 | ✅ WAL 模式适合读多写少场景 |

### 补充风险（审计识别）

| 零售风险 | 影响 | 建议缓解 |
|---------|------|---------|
| **Python 3.13 依赖兼容性** | chromadb/torch 在 Python 3.13 Windows 上可能无法安装 | Phase 1 前 2 天先做 pip install 验证；准备 pyproject.toml 声明 Python 3.12 兼容作为回退 |
| **watchdog Windows 稳定性** | Windows 下文件事件可能重复触发或漏触发 | 去抖5秒 + content_hash 比对双重保障；如无必要，可优先用定时扫描而非实时监控 |
| **HuggingFace 下载可及性** | 国内访问 HuggingFace 可能超时或失败 | 配置 mirror 镜像源（hf-mirror.com）；预下载模型打包进分发 |
| **config_center 持久化未决策** | 若 kb 配置走 config_center，重启后丢失 | Phase 1 前决定：kb 自管持久配置 vs config_center 加持久化层 |

### 风险分析评价

方案原有 6 项风险覆盖充分。运维验证官发现的 Python 3.13 兼容性风险是新增的第 7 项关键风险。我追加 3 项（watchdog 稳定性、HF 下载可及性、config_center 持久化决策）属于完善性补充，不构成方案缺陷。

**评价**：风险分析 **充分**，原表 + 验证意见补充已覆盖关键隐患。
